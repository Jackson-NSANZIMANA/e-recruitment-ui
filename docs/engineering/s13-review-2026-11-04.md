# S13 review — what I built, what I got wrong, and what it actually bought

**Date:** 2026-11-04
**Reviewed:** `a37b86e`, `0ada99c`, `e7a0773` on `arena/4f8fd39e-e-recruitment-ui`
**Method:** re-read every added file, then test each claim against the _built_ output and the token artefacts rather
than against the source I wrote. Where a claim could not be checked here, it is marked **unverified**.

Verdict up front: **the component shapes are sound; the evidence around them was weaker than the report
implied, and three of my claims were wrong.** Details in §2. The layer also does not yet do the job it was
built for (§4) — it ships capability, not visible change.

## 2. Three claims in my report were wrong

I checked these against the shipped artefacts, not my memory of writing them.

### 2.1 "It's a raised card" — the elevation pairing is only half implemented

The ADS elevation system pairs a surface with a shadow. `Card` takes the surface
(`elevation.surface.raised`) and **never sets a shadow**. Worse, in the atlassian-light theme
`elevation.surface.raised` resolves to `#FFFFFF` — exactly the same value as `elevation.surface`. So on the
default white page the "raised plane" is a 1px border and nothing else, which is the _exact_ treatment the
component's own comment says it exists to replace.

The `elevation.shadow.raised` token this component's comment claims as motivation appears in
`packages/ui/src` **only inside that comment**. (`NationalFrame` and `OfflineIndicator` use
`elevation.shadow.overlay`; `OfficialDocument` uses `.raised` — so the pairing is not foreign to this codebase,
which makes its absence on the one component whose comment advertises it worse.) It is a two-line fix and it is
not done. Root cause for the surface question is recorded in §5.2: tokens 20 moved which token sits at which
height, and the root dependency is still pinned at `^16.4.0`.

### 2.2 "No `…` is misused" — the aria props on those figures do nothing

`Sparkline` and `StackedBar` pass `aria-label` (and `aria-details`) to a `Box as="figure"`. **A `<figure>` with
no `aria-label`/`role` is `role=figure`, and `aria-label` on it is ignored by most AT**; the accessible name
comes from `<figcaption>`, which neither component renders. My render test used Testing Library's
`getByRole("figure", {name})`, which follows the ARIA name _computation_ but does not tell you a screen reader
will honour it.

The readings still reach a reader — the hidden `<table>` is announced — so this is not "the chart is
unlabelled". It is "the fix I claimed is only half a fix". What is actually missing is a `<figcaption>`
carrying the label as visible-or-hidden text, or an explicit `role="img"` on the `<svg>` with a `<title>`.
**Unverified in a real screen reader:** no Chromium or NVDA exists in this sandbox (§3), so this is read off
the ARIA spec and the rendered DOM, which is weaker evidence than the claim deserved.

### 2.3 "Nothing is below the 16px floor" — measurably false across the repo

Re-census, 2026-11-04, counting every `<Text` occurrence on a line (my first count was per-line only, which
undercounted components split over several lines):

```
total <Text> occurrences: 393
  no size (defaults to 14px): 280
  size="small"  (12px):      104
  size="medium" (14px):        6
  size="large"  (16px):        3
below the 16px floor:       390   (99.2%)
```

The floor is `MIN_BODY_TEXT_PX = 16` at `packages/design-system/src/a11y/index.ts:28`, and **nothing enforces
it**: `MIN_BODY_TEXT_PX` has no caller outside its own contract test. So the "floor" is a constant, not a gate,
which is the same hollow-gate pattern the repo's own anti-hollow gate exists to catch.

My layer adds to this: `Sparkline`'s hidden table uses `font.body.small` (12px), `StackedBar`'s legend and
`MetricCard`'s attention line use `size="medium"` (14px). I wrote the floor's name in a comment in `PageShell`
while shipping 14px two files away.

## 3. What could not be verified here, and what the report should have said

**No browser exists in this sandbox** — no Chromium, no Playwright browser cache, and the CDN is unreachable.
So:

- The screenshots in `S13.stories.tsx` have **never been rendered by a human or a browser**.
- `MetricCard`'s sparkline overflows its tile by ~43px at every realistic width (§4.2). That is arithmetic I

`docs/engineering/s13-layout-layer-2026-11-04.md` does say "rendered and asserted, not visually verified", which
is honest. It should have led with it instead of putting it in §6.

## 4. Design-level findings — the layer is not yet doing its job

### 4.1 Zero visual change on any screen

- No call site passes `trend` to `MetricCard`. **The sparkline, the trend delta and `goodDirection` render
  nowhere in the product.**
- No call site renders `StackedBar`. `panels.tsx` still draws five 100%-width stage tracks — the exact pattern
  `StackedBar` was written to replace — and still keeps `meterTrack`/`fill`/`fillWarning`/`stageTrack`.
- `Sparkline`'s only consumers are two stories and a test.

Those three charts account for roughly half the diff. Compared with what the gap doc promised (G1: "inflow vs
clearance over 5 days, queue-age distribution"), the dashboard is visually **the same page it was**, now with a
28px figure and a header that lines up. That is a real improvement; it is not what the section "chart layer"
implies.

### 4.2 `MetricCard` + `Sparkline` overflow by construction

`Sparkline` defaults to `width=220`, `MetricCard` never overrides it, and the console's metric grid is
`repeat(auto-fit, minmax(200px, 1fr))` inside a 1280px column with 24px card padding:

```
viewport 1440: 5 columns x 227px tile -> 177px of usable width; svg 220px -> 43px overflow
viewport  768: 3 columns x 224px tile -> 174px usable;           svg 220px -> 46px overflow
```

The svg is fixed-size, so on every layout the tile is _designed_ for, it is too wide. Fix: `width="100%"` +
`viewBox` + `preserveAspectRatio="none"` (as `StackedBar` already does), and let the caller size the tile.

### 4.3 A metric reading `0` during load is still a lie — in the new component

The admin dashboard passes `value={applications.data?.total ?? 0}` and friends. While any read is in flight,
the tiles render **0 open campaigns, 0 awaiting adjudication**. The page sets `ready={!isLoading}` for the
attention list and nothing for the metrics. The old `DashboardMetricCard` had the same defect; migrating to
`MetricCard` preserved it. A metric tile needs an explicit empty/unknown state — not `0`, which is a claim.

### 4.4 `Card`'s interactive affordances are broken, and it ships a dangling style

- `onClick` is destructured, used to compute `isInteractive` (so hover/active styles and `cursor: pointer`
  apply) and **never attached to any element**. The prop is typed `() => void` with no element, so it could not
  be keyboard-operable even if it were wired. It looks like the Jira template-picker pattern and behaves like
  a dead div.
- `styles['title']` is declared and never used.

Neither is reachable today (no caller passes `onClick`). They are traps for the next person.

### 4.5 Two dead exports

`seriesTokenAt` and `CHART_SERIES_TOKENS` are used only by `layout.test.ts`. `StackedBar` — their reason for
existing — reads the eight slots from its own module-scope `SERIES_FILL` array, because `token()` needs string
literals. So the wrap-around rule is tested in one place and implemented in another: the test proves a
function, not the component. The 8-slot table now exists twice.

Same pattern in `PAGE_INNER_PADDING` (0 callers — `PageShell` hardcodes `token("space.300")`), and
`Sparkline`'s `styles['table']` (declared, never applied; the `<table>` has no class).

### 4.6 390 nodes share one non-localising formatter

`MetricCard` prints `value.toLocaleString()` (locale of the browser). `Sparkline`, `StackedBar` and
`StackedBar`'s `aria-label` print `String(n)`. In French the figure reads `1 024`; the legend twelve pixels
below reads `1024`. There is no single `formatCount` and no locale in `@usrp/i18n`'s public surface. This is a
one-function fix, and it is the kind of inconsistency that makes a UI feel assembled rather than designed.

### 4.7 `MetricCard` is bloated for a tile, and its hierarchy is inverted

`Card` renders `padding: space.300` (24px), and `MetricCard` adds another `Stack space="space.100"` inside it:
a 5-tile row spends ~240px of horizontal space on padding. For a KPI the number should read first; here the
label is a heading on top and the number below it. Worth a `density="compact"` variant before this pattern is
copied to nine screens.

### 4.8 `SkeletonPanel` never stops

`@atlaskit/skeleton` ships `animation-iteration-count: infinite` and **no `prefers-reduced-motion` guard of its
own** — I removed the guard's last user in `StateBoundary` when I replaced the hand-rolled clip with
`@atlaskit/visually-hidden`. The shimmer therefore keeps moving for a reader who asked for stillness. This is
exactly gap **G4** in the doc this layer was built from.

## 5. State of the branch — it is behind `main`, and `main` moved under it

`main` is **3 commits ahead** (`11905b3`, `862a390`, `ed81680`) and two of those change the terms my work is
judged on:

### 5.1 A security fix my branch does not have, and a canary that reproduces it

`11905b3` rewrites all three `env.ts` files: Vite inlines the **whole** `import.meta.env` object wherever one
variable is read through a computed key or a cast, so `import.meta.env as Record<…>[key]` ships every `VITE_*`
variable of the build to the browser. My branch still has the computed-key form. I reproduced the shape of the
bug on this branch:

```
VITE_EDGE_URL=… VITE_UNRELATED_SECRET=CANARY_LEAK_9f3a2b  →  canary found in dist/assets/index-*.js
```

The fix is on `main`, not here. **`main` must be merged into this branch before it is proposed** — otherwise the
console ships the pre-fix env handling.

### 5.2 `main` also added guards that make two of my claims testable

- `tooling/repo-hygiene/verify-font-faces.mjs` + the `@compiled__css@3.1.0` patch: before it, every `@font-face`
  in the design-system stylesheet was merged into one rule and the UI rendered in a system font. **Every CSS
  extraction and screenshot I produced on this branch predates that patch.** My extraction numbers are fine;
  my _rendering_ assumptions are untested against it.
- `verify-bundle-env.mjs` is the gate for §5.1.

### 5.3 Overlap is small

Only `apps/officer-console/vite.config.ts` (they added a service-worker `revision` comment block near mine) and
`pnpm-lock.yaml` conflict. Both are mechanical.

## 6. The gate that would have caught most of §2 and §4

`G6` in the gap doc — "nothing proves what a screen looks like" — is still open, and it is the root cause of
this review existing at all: 390/393 text nodes below the floor shipped because nothing measured it; a 220px
svg in a 177px tile shipped because nothing rendered it.

Today: **128 source `.tsx` files, 4 stories.** `pnpm a11y` runs only what has a story. There is no
`toHaveScreenshot` baseline. Every one of the findings above is visible in one screenshot.

## 8. Recommendation, in dependency order

1. **Merge `origin/main` into this branch.** Non-negotiable: it carries the env fix (§5.1) and the
   font-face patch (§5.2) that every render depends on.
2. **Finish the elevation pairing** (`elevation.shadow.raised`) and decide the raised-vs-default surface
   question against tokens 20 (§2.1) — a decision, not a patch, because it touches the palette strategy.
3. **Make the charts responsive and give `Card` the `aria` it claims**: `figcaption` or `role="img"` + `<title>`;
   `width="100%"` svg (§2.2, §4.2).
4. **Wire the charts to real data.** One `Sparkline` on one queue and one `StackedBar` replacing the five stage
   tracks turns G1 from "capability" into "the page changed" (§4.1).
5. **Enforce the 16px floor as a lint rule**, then fix the 390 — in that order, or the number grows back
   (§2.3, §6).
6. **`G6` properly**: stories for every component in `@usrp/ui`, `toHaveScreenshot` baselines, and the a11y
   script pointed at the whole gallery.
7. Small, cheap, do-with-#1: dead code (§4.5), `onClick` (§4.4), `formatCount` (§4.6), reduced-motion for the
   skeleton (§4.8), and an unknown state for loading metrics (§4.3).
